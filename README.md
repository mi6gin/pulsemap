# PulseMap

Тестовое задание на Laravel 13 и Vue 3: авторизованный пользователь сохраняет ссылку на организацию в Яндекс Картах, запускает фоновую синхронизацию и просматривает точные показатели организации и все полученные отзывы.

## Демо

Публичный URL будет добавлен после развёртывания. Это единственный пункт формата сдачи, который намеренно оставлен за пределами репозитория.

Готовые варианты развёртывания и финальный чек-лист находятся в [`DEPLOYMENT.md`](DEPLOYMENT.md). Для Render добавлен Blueprint `render.yaml`; для VPS — `compose.production.yaml` и `.env.production.example`.

## Что реализовано

- вход по сессии Laravel Sanctum; тестовый пользователь создаётся сидером;
- одна настраиваемая организация на пользователя и строгая проверка полного URL карточки, ссылки с `oid` или короткой ссылки Яндекс Карт;
- асинхронная синхронизация через Laravel Queue, прогресс, повторный запуск и понятное состояние ошибки;
- название, рейтинг, точное количество оценок и точное количество отзывов отдельно от числа сохранённых записей;
- отзывы с автором, аватаром, датой, текстом и оценкой;
- отзывы, которым источник возвращает `rating: 0`, сохраняются и помечаются как «Без оценки», не прерывая весь импорт;
- серверная пагинация ровно по 50 отзывов;
- идемпотентный `upsert`: повторная синхронизация обновляет существующие отзывы и удаляет исчезнувшие, не создавая дубликаты;
- история изменений показателей организации;
- адаптивный SPA-интерфейс на Vue 3 Composition API и Tailwind CSS 4;
- SQLite по умолчанию, Docker Compose, CI и автоматические тесты.

## Быстрый локальный запуск

Требования: PHP 8.3+, Composer 2, Node.js 22+ и SQLite.

```bash
composer setup
php artisan db:seed
composer run dev
```

Откройте [http://localhost:8000](http://localhost:8000).

Данные для входа:

```text
demo@example.com
password
```

`composer run dev` одновременно запускает HTTP-сервер, Vite и обработчик очереди. Если процессы запускаются раздельно, обработчик обязателен:

```bash
php artisan serve
npm run dev
php artisan queue:work --tries=4 --timeout=180
```

## Переменные окружения

Базовые Laravel-переменные находятся в `.env.example`. Для парсера доступны:

| Переменная | По умолчанию | Назначение |
| --- | ---: | --- |
| `YANDEX_MAPS_CONNECT_TIMEOUT` | `10` | таймаут соединения, секунды |
| `YANDEX_MAPS_TIMEOUT` | `25` | полный таймаут HTTP-запроса, секунды |
| `YANDEX_MAPS_PAGE_SIZE` | `50` | ожидаемый размер страницы источника |
| `YANDEX_MAPS_MAX_PAGES` | `20` | предохранитель от бесконечной пагинации |
| `YANDEX_MAPS_AVAILABLE_REVIEWS_LIMIT` | `600` | ожидаемый предел доступной выдачи Яндекса |
| `YANDEX_MAPS_DELAY_MIN_MS` | `250` | минимальная пауза между страницами |
| `YANDEX_MAPS_DELAY_MAX_MS` | `650` | максимальная пауза между страницами |
| `YANDEX_MAPS_REQUESTS_PER_MINUTE` | `12` | общий лимит запросов для всех jobs |
| `YANDEX_MAPS_PROXY` | пусто | необязательный HTTP(S)-прокси Guzzle |

Для production обязательно задаются собственные `APP_KEY`, `APP_URL`, параметры постоянной БД, `QUEUE_CONNECTION` и общее cache-хранилище. Веб-приложение и worker должны использовать одну БД и один cache.

## Запуск через Docker

Сначала подготовьте окружение и ключ приложения:

```bash
cp .env.example .env
docker compose build
docker compose run --rm --no-deps --entrypoint php app artisan key:generate
docker compose up -d
docker compose exec app php artisan db:seed
```

Приложение будет доступно на [http://localhost:8000](http://localhost:8000). Если порт занят, запустите `APP_PORT=8018 docker compose up -d` и откройте `http://localhost:8018`. Контейнер `worker` запускается после успешной проверки `/up` и обрабатывает синхронизации, а `app` выполняет миграции при старте. Каталоги `database` и `storage` подключены с хоста, поэтому данные сохраняются после пересборки контейнеров.

Тесты покрывают аутентификацию, авторизацию данных разных пользователей, валидацию URL, раздельные счётчики источника и сохранённых отзывов, пагинацию, постановку задания в очередь, успешную и ошибочную синхронизацию, идемпотентность, лимитирование внешних запросов и изменение формата ответа источника. Внешние HTTP-запросы в тестах запрещены и заменены фикстурами. Эти же проверки автоматически выполняются в GitHub Actions.

## Как устроена синхронизация

1. `PUT /api/organization` сохраняет URL и ставит уникальное задание `SyncOrganization` в очередь.
2. Задание получает HTML публичной карточки с браузерными заголовками и cookie jar, безопасно следует только по разрешённым доменам Яндекса.
3. Из встроенного JSON извлекаются структурированные отзывы. Серверная пагинация Яндекс Карт `?page=N` отдаёт по 50 записей; страницы загружаются последовательно до заявленного количества или конца выдачи.
4. Метрики сверяются с JSON и schema.org meta-тегами. Название и точные счётчики обязательны: при их исчезновении синхронизация завершается явной ошибкой, а старые данные остаются доступны.
5. В одной транзакции выполняются `upsert`, удаление устаревших строк, обновление организации и создание snapshot только при реальном изменении показателей.

Выбран разбор структурированного JSON из серверного HTML, а не Playwright. Такой подход быстрее, требует заметно меньше CPU/RAM, не нуждается в Chromium и проще разворачивается в очереди. Его минус — зависимость от внутренних ключей и от того, продолжит ли Яндекс включать данные в HTML. Headless-браузер ближе воспроизводит реальное поведение пользователя и умеет загружать отзывы прокруткой, но заметно медленнее, тяжелее в эксплуатации и также уязвим к смене DOM, browser fingerprinting и CAPTCHA. Парсер изолирован в `YandexMapsParser`; при изменении источника его можно заменить на headless-реализацию без изменения API, очереди и интерфейса.

## Устойчивость и ограничения запросов

- уникальное queue-задание не позволяет одновременно синхронизировать одну и ту же ссылку организации;
- задание запоминает исходную ссылку и отбрасывает устаревший результат, если пользователь сменил карточку во время синхронизации;
- HTTP timeout, четыре попытки задания и экспоненциальные интервалы 15/60/180 секунд;
- на уровне HTTP и очереди повторяются сетевые ошибки, ответы 403/429 и 5xx; несовместимый формат и 404 сразу переводят организацию в состояние ошибки;
- перед каждой HTTP-попыткой применяется общий для всех jobs лимитер 12 запросов в минуту; между страницами добавляется случайная задержка 250–650 мс;
- User-Agent выбирается случайно из конфигурации, а лимитер использует общее cache-хранилище, поэтому действует и при нескольких worker-процессах;
- опциональный прокси задаётся через `YANDEX_MAPS_PROXY`;
- редиректы проверяются вручную, что закрывает SSRF через чужой домен;
- `YANDEX_MAPS_MAX_PAGES=20` покрывает до 1000 отзывов при размере страницы 50. Лимит можно увеличить без изменения кода.
- `YANDEX_MAPS_AVAILABLE_REVIEWS_LIMIT=600` задаёт ожидаемый лимит доступной выдачи Яндекса; прежние данные не заменяются, если парсер получил меньше ожидаемого количества.

Парсинг публичных страниц зависит от разметки внешнего сервиса и должен использоваться с учётом условий Яндекса и применимого законодательства. Код не обходит CAPTCHA и не маскирует блокировку: 403/429 переводятся в управляемую повторную попытку, несовместимый формат — в диагностируемую ошибку.

## API

Все `/api/*`, кроме входа через web-route, защищены `auth:sanctum`.

| Метод | Адрес | Назначение |
| --- | --- | --- |
| `POST` | `/login` | Вход и ротация сессии |
| `POST` | `/logout` | Выход |
| `GET` | `/api/me` | Текущий пользователь |
| `GET` | `/api/organization` | Организация, состояние и история |
| `PUT` | `/api/organization` | Сохранить URL и запустить импорт |

| `GET` | `/api/organization/reviews?page=N` | Отзывы, 50 на страницу |

## Ответы на дополнительные требования

### 1. Устойчивость к смене разметки

Парсер не считает пустой или частичный ответ успехом. Он проверяет минимальный размер HTML, наличие ID организации, названия, точных `ratingCount` и `reviewCount`, структуру каждого отзыва, количество полученных уникальных отзывов и преждевременное окончание пагинации. Несовместимый ответ вызывает `YandexMapsParsingException`, записывается в лог и переводит организацию в `failed`; сетевые ограничения переводят её в `retrying`. Запись в БД выполняется одной транзакцией только после полной проверки результата, поэтому ошибка источника не уничтожает последний успешный снимок.

### 2. Выбор способа парсинга

Используется структурированный JSON серверных HTML-страниц и серверная пагинация `?page=N`, а не Playwright. Это быстрее, требует меньше CPU/RAM, не нуждается в Chromium и проще запускается в очереди. Риски — зависимость от внутренних ключей, параметра пагинации и наличия JSON в HTML. Headless-браузер лучше воспроизводит прокрутку и выполнение JavaScript, но медленнее, дороже, сложнее масштабируется и также зависит от DOM, fingerprinting и CAPTCHA. `YandexMapsParser` изолирует этот риск: headless-адаптер можно добавить без изменения API, job и Vue-интерфейса.

### 3. Масштаб и фоновая обработка

HTTP-запрос только сохраняет настройку и ставит уникальный `SyncOrganization` в Laravel Queue. Job имеет четыре попытки, backoff `15/60/180`, timeout 180 секунд и сообщает прогресс после каждой страницы. Несколько worker-процессов могут обрабатывать разные организации параллельно, а общий rate limiter ограничивает совокупную нагрузку. Для сети из 50 филиалов production-модель должна заменить уникальный `organizations.user_id` на связь `organization_user`/`account_id`, после чего планировщик создаёт по одной уникальной job на филиал; API статуса и сам parser менять не требуется.

### 4. Анти-бан на объёме

Реализованы общий троттлинг, случайные паузы, ограниченные повторы, экспоненциальный backoff, browser-like заголовки, cookie jar, ротация User-Agent и необязательный прокси. Ответы 403/429 не маскируются: синхронизация получает статус `retrying`, после исчерпания попыток — `failed`. В production для регулярной синхронизации 50 филиалов нужен пул прокси с health-check, стабильный User-Agent в пределах одной сессии, случайное расписание без одновременного старта всех филиалов и circuit breaker, временно останавливающий источник при всплеске 403/429.

### 5. Идемпотентность и история

Отзывы уникальны по `(organization_id, source_review_id)`: повторный запуск делает `upsert`, обновляет изменившиеся поля и удаляет записи, исчезнувшие из полной выдачи. `organization_snapshots` хранит значения показателей и JSON `changes` вида `{field: {from, to}}`, поэтому изменение рейтинга и счётчиков видно как «было → стало».

Если нужна история состава отзывов, модель расширяется таблицами `sync_runs` (`organization_id`, время, статус, counters) и `review_versions` (`sync_run_id`, `source_review_id`, hash содержимого, автор, дата, текст, оценка, change_type`). При синхронизации hash сравнивается с последней версией; версия создаётся только для `added`, `updated` или `removed`. Это сохраняет аудит изменений без полного дублирования всех ~600 записей на каждом запуске.

## Что доделал бы, имея больше времени

- добавил плановую синхронизацию, метрики длительности и алерты на рост ошибок парсинга;
- для production заменил SQLite и database cache на PostgreSQL и Redis, а статический прокси — на управляемый пул с health-check;
- добавил второй headless-адаптер как fallback и регулярный контрактный smoke-тест на нескольких публичных карточках;
- расширил историю до снимков состава отзывов и отдельного сравнения добавленных, изменённых и исчезнувших записей.

## Развёртывание

Production-среде нужны PHP 8.3+, веб-сервер, постоянная БД, отдельный `queue:work`, собранный `public/build`, HTTPS и собственные значения `APP_KEY`, `APP_URL` и переменных БД. После деплоя выполните:

```bash
php artisan migrate --force
php artisan db:seed --force
php artisan optimize
php artisan queue:restart
```

Docker-образ уже содержит production-сборку фронтенда и PHP-зависимости. Публичный URL задаётся через `APP_URL` конкретной площадки и не зашивается в репозиторий.

Полная инструкция для Render и Docker Compose на VPS приведена в [`DEPLOYMENT.md`](DEPLOYMENT.md).
