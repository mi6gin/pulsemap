# PulseMap

Тестовое задание на Laravel 13 и Vue 3: авторизованный пользователь сохраняет ссылку на организацию в Яндекс Картах, запускает фоновую синхронизацию и просматривает точные показатели организации и все полученные отзывы.

## Что реализовано

- вход по сессии Laravel Sanctum; тестовый пользователь создаётся сидером;
- одна настраиваемая организация на пользователя и строгая проверка URL Яндекс Карт;
- асинхронная синхронизация через Laravel Queue, прогресс, повторный запуск и понятное состояние ошибки;
- название, рейтинг, точное количество оценок и точное количество отзывов отдельно от числа сохранённых записей;
- отзывы с автором, аватаром, датой, текстом и оценкой;
- серверная пагинация ровно по 50 отзывов;
- идемпотентный `upsert`: повторная синхронизация обновляет существующие отзывы и удаляет исчезнувшие, не создавая дубликаты;
- история изменений показателей организации;
- адаптивный SPA-интерфейс на Vue 3 Composition API и Tailwind CSS 4;
- SQLite по умолчанию, Docker Compose, CI и автоматические тесты.

## Быстрый локальный запуск

Требования: PHP 8.3+, Composer 2, Node.js 22+ и SQLite.

```bash
composer setup
php artisan db:seed
composer run dev
```

Откройте [http://localhost:8000](http://localhost:8000).

Данные для входа:

```text
demo@example.com
password
```

`composer run dev` одновременно запускает HTTP-сервер, Vite и обработчик очереди. Если процессы запускаются раздельно, обработчик обязателен:

```bash
php artisan serve
npm run dev
php artisan queue:work --tries=4 --timeout=180
```

## Запуск через Docker

Сначала подготовьте окружение и ключ приложения:

```bash
cp .env.example .env
docker compose build
docker compose run --rm --no-deps --entrypoint php app artisan key:generate
docker compose up -d
docker compose exec app php artisan db:seed
```

Приложение будет доступно на [http://localhost:8000](http://localhost:8000). Контейнер `worker` запускается после успешной проверки `/up` и обрабатывает синхронизации, а `app` выполняет миграции при старте. Каталоги `database` и `storage` подключены с хоста, поэтому данные сохраняются после пересборки контейнеров.

## Проверки

```bash
vendor/bin/pint --test
php artisan test --compact
npm run build
```

Тесты покрывают аутентификацию, авторизацию данных разных пользователей, валидацию URL, раздельные счётчики источника и сохранённых отзывов, пагинацию, постановку задания в очередь, успешную и ошибочную синхронизацию, идемпотентность, лимитирование внешних запросов и изменение формата ответа источника. Внешние HTTP-запросы в тестах запрещены и заменены фикстурами. Эти же проверки автоматически выполняются в GitHub Actions.

## Как устроена синхронизация

1. `PUT /api/organization` сохраняет URL и ставит уникальное задание `SyncOrganization` в очередь.
2. Задание получает HTML публичной карточки с браузерными заголовками и cookie jar, безопасно следует только по разрешённым доменам Яндекса.
3. Из встроенного JSON извлекаются структурированные отзывы. Серверная пагинация Яндекс Карт `?page=N` отдаёт по 50 записей; страницы загружаются последовательно до заявленного количества или конца выдачи.
4. Метрики сверяются с JSON и schema.org meta-тегами. При исчезновении обязательных полей синхронизация завершается явной ошибкой, а старые данные остаются доступны.
5. В одной транзакции выполняются `upsert`, удаление устаревших строк, обновление организации и создание snapshot только при реальном изменении показателей.

Выбран разбор структурированного JSON из серверного HTML, а не Playwright. Такой подход быстрее, требует заметно меньше CPU/RAM, не нуждается в Chromium и проще разворачивается в очереди. Его минус — зависимость от внутренних ключей и от того, продолжит ли Яндекс включать данные в HTML. Headless-браузер ближе воспроизводит реальное поведение пользователя и умеет загружать отзывы прокруткой, но заметно медленнее, тяжелее в эксплуатации и также уязвим к смене DOM, browser fingerprinting и CAPTCHA. Парсер изолирован в `YandexMapsParser`; при изменении источника его можно заменить на headless-реализацию без изменения API, очереди и интерфейса.

## Устойчивость и ограничения запросов

- уникальное queue-задание не позволяет одновременно синхронизировать одну организацию;
- HTTP timeout, четыре попытки задания и экспоненциальные интервалы 15/60/180 секунд;
- на уровне HTTP и очереди повторяются сетевые ошибки, ответы 403/429 и 5xx; несовместимый формат и 404 сразу переводят организацию в состояние ошибки;
- перед каждой HTTP-попыткой применяется общий для всех jobs лимитер 12 запросов в минуту; между страницами добавляется случайная задержка 250–650 мс;
- User-Agent выбирается случайно из конфигурации, а лимитер использует общее cache-хранилище, поэтому действует и при нескольких worker-процессах;
- опциональный прокси задаётся через `YANDEX_MAPS_PROXY`;
- редиректы проверяются вручную, что закрывает SSRF через чужой домен;
- `YANDEX_MAPS_MAX_PAGES=20` покрывает до 1000 отзывов при размере страницы 50. Лимит можно увеличить без изменения кода.

Парсинг публичных страниц зависит от разметки внешнего сервиса и должен использоваться с учётом условий Яндекса и применимого законодательства. Код не обходит CAPTCHA и не маскирует блокировку: 403/429 переводятся в управляемую повторную попытку, несовместимый формат — в диагностируемую ошибку.

## API

Все `/api/*`, кроме входа через web-route, защищены `auth:sanctum`.

| Метод | Адрес | Назначение |
| --- | --- | --- |
| `POST` | `/login` | Вход и ротация сессии |
| `POST` | `/logout` | Выход |
| `GET` | `/api/me` | Текущий пользователь |
| `GET` | `/api/organization` | Организация, состояние и история |
| `PUT` | `/api/organization` | Сохранить URL и запустить импорт |
| `POST` | `/api/organization/sync` | Повторить синхронизацию |
| `GET` | `/api/organization/reviews?page=N` | Отзывы, 50 на страницу |

## Основные решения по пунктам ТЗ

1. **Источник данных:** структурированные данные серверных страниц Яндекс Карт с отдельным адаптером и fail-fast проверкой схемы.
2. **Все отзывы:** серверная пагинация источника, очередь, отображение прогресса и локальная пагинация БД.
3. **Защита от ограничений:** rate limiter, jitter, ограниченные retries, timeout, User-Agent rotation и поддержка прокси.
4. **Изменения данных:** уникальные внешние ID, `upsert`, удаление исчезнувших отзывов и snapshots показателей.
5. **Фоновые задачи:** database queue; HTTP-запрос отвечает сразу, интерфейс опрашивает компактный статус, ошибки сохраняются и доступны для повторного запуска.

## Что доделал бы, имея больше времени

- добавил плановую синхронизацию, метрики длительности и алерты на рост ошибок парсинга;
- для production заменил SQLite и database cache на PostgreSQL и Redis, а статический прокси — на управляемый пул с health-check;
- добавил второй headless-адаптер как fallback и регулярный контрактный smoke-тест на нескольких публичных карточках;
- расширил историю до снимков состава отзывов и отдельного сравнения добавленных, изменённых и исчезнувших записей.

## Развёртывание

Production-среде нужны PHP 8.3+, веб-сервер, постоянная БД, отдельный `queue:work`, собранный `public/build`, HTTPS и собственные значения `APP_KEY`, `APP_URL` и переменных БД. После деплоя выполните:

```bash
php artisan migrate --force
php artisan db:seed --force
php artisan optimize
php artisan queue:restart
```

Docker-образ уже содержит production-сборку фронтенда и PHP-зависимости. Публичный URL задаётся через `APP_URL` конкретной площадки и не зашивается в репозиторий.
